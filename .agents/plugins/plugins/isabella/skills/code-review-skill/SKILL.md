# Code Review Skill

Transform code reviews from gatekeeping to knowledge sharing through constructive feedback,
systematic analysis, and collaborative improvement — grounded in how *this* repository actually
works, not in an assumed stack.

## Runtime portability

Use the capability available in the current runtime, not the literal Claude tool names in older
instructions: invoke a skill when it is available; otherwise read its `SKILL.md` directly.
For parallel review, Claude Code uses `Agent`/`Task`; Codex uses `spawn_agent` and
`wait_agent`. If delegation is unavailable, run the applicable axes sequentially. Ask any
necessary user question through the runtime's normal prompt/input mechanism, and use its available
web tool for current external documentation.

## Ground the review in this repo first

This skill makes no assumption about language, framework, or monorepo layout. It reads
`PROJECT_MAP.md` (generated by the `project-map` skill) to learn the real stack, architecture,
and conventions before reviewing anything.

```bash
cat PROJECT_MAP.md 2>/dev/null | head -20
```

- **Exists:** read §1 (identidade), §2-3 (stack/frameworks), §4 (arquitetura e estrutura real),
  §11 (convenções observadas), and §5 if the change touches frontend. Keep this in context — it
  feeds every sub-agent brief below.
- **Doesn't exist:** tell the user — "Não encontrei `PROJECT_MAP.md` na raiz do repositório. Sem
  ele, o review vai usar só heurísticas genéricas (SOLID + OWASP + anti-padrões universais), sem
  saber a stack e as convenções reais deste repo. Posso rodar a skill `project-map` primeiro?" —
  and wait for confirmation.
  - **Accepts:** invoke `project-map`, wait for it to finish, then re-read
    `PROJECT_MAP.md`.
  - **Declines:** proceed with only the stack-agnostic guides below (Architecture, Performance,
    Security, Universal Quality) and say so in the final report — findings that would normally
    cite a documented repo convention will instead fall back to generic judgement calls.

Also re-read the repo's own `CLAUDE.md`/`CONTRIBUTING.md` if present — those take precedence over
anything generic in this skill or its guides.

## Core Principles

### 1. The Review Mindset

**Goals of Code Review:**
- Catch bugs and edge cases
- Ensure code maintainability
- Share knowledge across the team
- Enforce this repo's actual standards (`PROJECT_MAP.md` §11, plus any `CLAUDE.md`/`CONTRIBUTING.md`)
- Improve design and architecture
- Build team culture

**Not the Goals:**
- Show off knowledge
- Nitpick formatting — lint/format tooling already enforces this (check `PROJECT_MAP.md` §3 for which)
- Block progress unnecessarily
- Rewrite to your preference when the existing pattern already works

### 2. Effective Feedback

**Good Feedback is:**
- Specific and actionable
- Educational, not judgmental
- Focused on the code, not the person
- Balanced (praise good work too)
- Prioritized (critical vs nice-to-have)

Write comments for humans in whatever language this repo's PRs/commits actually use — check
`CLAUDE.md`/`CONTRIBUTING.md` first, then fall back to the predominant language observed in past
PR comments or commit messages. Code, identifiers, and this skill's own reference material stay
in English regardless.

```markdown
❌ Bad: "This is wrong."
✅ Good: "This can cause a race condition when multiple users hit it concurrently — worth
        wrapping in [this repo's transaction/unit-of-work pattern, per PROJECT_MAP.md §3]?"

❌ Bad: "Why didn't you handle the error case?"
✅ Good: "This throws directly instead of [this repo's documented error-handling pattern] —
        would that be more consistent with the rest of the module?"

❌ Bad: "Rename this variable."
✅ Good: "[nit] `uc` → `userCount` would read clearer. Not blocking."
```

### 3. Review Scope

**What to Review:**
- Logic correctness and edge cases
- Security vulnerabilities
- Performance implications (N+1 queries, unnecessary re-renders/re-fetches — whichever apply to the stack)
- Test coverage and quality (per `PROJECT_MAP.md` §6 conventions)
- Error handling, per this repo's documented pattern
- API design and naming, module/context boundaries
- Fit with existing architecture (`PROJECT_MAP.md` §4)

**What Not to Review Manually:**
- Code formatting — whatever lint/format tool `PROJECT_MAP.md` §3 names already enforces this
- Import organization, only where it's a real convention (e.g. an alias vs. relative imports), not ordering
- Simple typos

## Review Process

### Phase 1: Context Gathering (main agent, sequential — 2-5 minutes)

1. Read the PR description and linked issue (tracker per `PROJECT_MAP.md` §13)
2. Check PR size (>400 lines? suggest splitting)
3. Review CI status — gates per `PROJECT_MAP.md` §8 (lint, type-check, tests passing?)
4. Understand the business requirement in the repo's own domain terms
5. In a monorepo, note which workspace(s) the change touches (`PROJECT_MAP.md` §2 rows) — CI is
   sometimes scoped by path, so cross-cutting changes need extra care
6. Identify the spec/issue source, in this order: issue reference in commit messages → a path
   given by the user → a spec file under `docs/`, `specs/`, or `.specs/` matching the branch name
   → ask the user. None found and the user says there isn't one? The Spec axis (Phase 2) is
   skipped and the final report notes "no spec available" instead of guessing.
7. Pin the diff: `git diff <fixed-point>...HEAD` (three-dot, against the merge-base) plus
   `git log <fixed-point>..HEAD --oneline` for the commit list. Confirm the ref resolves and the
   diff is non-empty before spawning anything — a bad ref should fail here, not inside a sub-agent.
8. Optional, for large diffs: pipe the diff through
   [`scripts/pr-analyzer.ts`](scripts/pr-analyzer.ts)
   (`git diff <fixed-point>...HEAD | npx tsx scripts/pr-analyzer.ts --stats`) to triage complexity
   and flag risk factors (missing tests, migrations touched, security-sensitive files) before
   reading line by line.

### Phase 2: Parallel sub-agent review

Spawn one sub-agent per applicable axis, **in a single message so they run concurrently** — each
sub-agent gets its own context so one axis's findings don't bias another's. Give every sub-agent:
the diff command and commit list from Phase 1, the full contents of its reference guide(s) pasted
inline (a sub-agent has no other access to them), and the relevant `PROJECT_MAP.md` excerpt.

| Axis | Reference(s) pasted in | Brief |
|---|---|---|
| **Architecture** | `architecture-review-guide.md` + `PROJECT_MAP.md` §4/§11 + any matched stack guide | Does the diff fit this repo's documented architecture (module/context boundaries, layering)? Report violations of a *documented* pattern as hard findings, and SOLID/coupling/cohesion issues as judgement calls. Under 400 words. |
| **Correctness & Security** | `common-bugs-checklist.md` + `security-review-guide.md` | Logic bugs, edge cases, race conditions, and OWASP-style issues (input validation, authz, secrets). Quote the hunk/file for each finding. Under 400 words. |
| **Performance** | `performance-review-guide.md` | N+1 queries, algorithmic complexity, unnecessary client-side fetching/re-rendering, missing pagination — whichever apply to the stack in `PROJECT_MAP.md`. Under 400 words. |
| **Quality & Reuse** | `code-quality-universal.md` | Reuse audit (search for an existing utility/hook/component before accepting new code) plus anti-patterns: parameter sprawl, leaky abstractions, nested conditionals, stringly-typed code, TOCTOU, no-op updates, redundant state. Also runs the **CRAP check** below and reports every function over threshold with its snippet. Under 400 words (the CRAP findings don't count against this cap). |
| **Spec conformance** *(only if a spec/issue source was found in Phase 1 step 6)* | The spec/issue contents | Go through **every requirement in the spec** and check it got implemented — this list must come out complete, nothing skipped. Report: (a) 🔴/🟡 requirements missing or only partially implemented — this is the one that blocks, quote the spec line; (b) 🟡 requirements that look implemented but wrong, quote the spec line and the diff hunk; (c) 🟢 behavior in the diff the spec didn't ask for — flag it as an FYI ("fora do escopo da spec"), not a defect: extra implementation beyond the spec is fine on its own, it's only worth a second look if it conflicts with a requirement or changes something the spec didn't mean to touch. Under 400 words. |

If `PROJECT_MAP.md` doesn't exist and the user declined generating it, the Architecture axis
drops the "documented pattern" half and reports only the stack-agnostic SOLID/coupling read — say
so in the aggregated report.

> **Optional: over-engineering pass.** If the `ponytail:ponytail-review` skill is available
> (third-party plugin, not every setup has it), fold it into the Quality & Reuse axis — run it
> after that sub-agent returns, and merge its findings into the same axis's report instead of a
> separate one. Ponytail findings have no severity of their own — map them to this skill's tiers:
> 🟢 `[nit]` by default, 🟡 `[important]` only if the over-engineering is a real maintainability
> risk (e.g. an unneeded dependency).

### CRAP check (run by the Quality & Reuse sub-agent)

The Quality & Reuse sub-agent runs this itself (it has `Bash`) as part of its brief — it's not a
separate, skippable pass. It combines cyclomatic complexity and measured coverage into one risk
score for changed production functions:

`CRAP = complexity² × (1 - coverage)³ + complexity`

Run it only when the repository can generate a current coverage JSON report. Do not infer
coverage — if the report or its dependencies are unavailable, say so in the axis's report as
inconclusive instead of guessing. A low score never proves correctness: a test without a
meaningful assertion can lower it.

1. Obtain coverage for the relevant test suite (full scope, not just tests added in the change).
2. Write the changed production file paths, one per line, to a temporary file.
3. Run the calculator for the project language, with **threshold 20**:

```bash
# TypeScript/JavaScript: requires eslintcc and an Istanbul coverage-final.json report.
node <skill-dir>/tools/crap_calculator.ts --coverage-json coverage/coverage-final.json --source-dir . --only-from /tmp/crap-files.txt --threshold 20 --json-out /tmp/crap.json

# Python: requires radon and a coverage.py JSON report.
python <skill-dir>/tools/crap_calculator.py --coverage-json coverage.json --source-dir . --only-from /tmp/crap-files.txt --threshold 20 --json-out /tmp/crap.json
```

4. **Every function in `high_risk_functions` (CRAP > 20) is a required finding, not a suggestion
   to consider dropping.** For each one: `Read` its file (the JSON only gives `file` + `name`,
   not line numbers — locate the function by name) and quote the actual function body in the
   finding, alongside its `crap`/`comp`/`cov` values, so the reviewer sees exactly what to
   simplify or cover with a test without having to go find it themselves.
5. Do not request superficial tests just to lower CRAP. Say whether the fix should be reducing
   branching or adding a meaningful test — a finding is justified only by an actual correctness,
   maintainability, or test-quality concern.

The calculators are self-contained in this skill's `tools/` directory. Keep the JSON report
outside versioned source unless the repository explicitly requires review artifacts.

### Phase 3: Aggregate — one section per axis, never merged

Present each sub-agent's report verbatim (or lightly cleaned) under its own heading: `## Architecture`,
`## Correctness & Security`, `## Performance`, `## Quality & Reuse`, and `## Spec` when it ran. **Do
not merge or rerank findings across axes** — a change can pass one axis and fail another (code that
follows every convention but implements the wrong thing is an Architecture pass / Spec fail; code
that does exactly what the issue asked but breaks the repo's conventions is a Spec pass /
Architecture fail). Reporting them separately stops one axis from masking a problem the others
found. End with a one-line summary per axis: finding count and the worst issue *within that axis*.

### Phase 4: Summary & Decision (2-3 minutes)

1. Summarize key concerns (per axis, from Phase 3)
2. Highlight what you liked
3. Make a clear decision:
   - ✅ Approve
   - 💬 Comment (minor suggestions)
   - 🔄 Request Changes (must address)
4. Offer to pair if complex

## Review Techniques

### Technique 1: The Checklist Method

Use [`assets/review-checklist.md`](assets/review-checklist.md) for a consistent quick pass, and
[Security Review Guide](reference/security-review-guide.md) for a deeper security pass.

### Technique 2: The Question Approach

Instead of stating problems, ask questions:

```markdown
❌ "This will break if the list comes back empty."
✅ "What happens if `items` comes back as an empty array?"

❌ "This needs error handling."
✅ "How should this behave if the API call fails?"
```

### Technique 3: Suggest, Don't Command

```markdown
❌ "Change this to use [pattern]."
✅ "Suggestion: wrapping this in [this repo's documented pattern] would keep it consistent
   with the rest of the module. What do you think?"

❌ "Extract this into a hook/helper."
✅ "This fetch logic shows up in 3 components. Would it make sense to extract it into a
   shared helper, per PROJECT_MAP.md §4's 'where things go' table?"
```

### Technique 4: Differentiate Severity

- 🔴 `[blocking]` — Must fix before merge
- 🟡 `[important]` — Should fix, discuss if disagree
- 🟢 `[nit]` — Nice to have, not blocking
- 💡 `[suggestion]` — Alternative approach to consider
- 📚 `[learning]` — Educational comment, no action needed
- 🎉 `[praise]` — Good work, keep it up!

**Severity levels:** 🔴 / 🟡 / 🟢 are the three severity tiers used as the standard across all
guides in this skill, and every sub-agent axis in Phase 2 tags its findings with them — 🔴 blocks
the merge, 🟡 should be addressed, 🟢 is optional. The remaining markers (💡 / 📚 / 🎉) are
non-blocking annotations.
